# zero-to-design Token 消耗优化分析

## 目标与边界

分别降低两类完整任务从开始到交付的总 Token：

- **首次设计任务**：从尚无获批设计规范，到首批预览与 `DESIGN.md` 获批。
- **持续设计任务**：以已有权威设计来源为起点，完成新增页面、组件或局部改动并获批。

保留用户对设计方向与产物的选择权、可运行预览、最终 `DESIGN.md`、跨会话恢复和现有批准门槛。阶段 5 首批 3–5 页的建议规模及可选分流不变。阶段 3 首轮固定展示三个方向，三个方向仍各有现行要求的完整规格与可视预览。参考收集可按已有证据调整数量和类别；信息不足时继续补齐。产物批准时可默认展示摘要、变化和文件链接，用户要求时展示全文。

## 开销路径

### 首次设计

1. 大型 `SKILL.md` 在进入任一阶段时先加载。即使任务尚处于产品定义，模型也会看到已有系统、后续打磨与最终固化规则。
2. 阶段 2 默认整理 5–10 个参考并覆盖四类；当用户已给出可核实的品牌资产、参考和明确偏好时，仍会发生不必要的补齐与反馈轮次。
3. 阶段 3 为每个候选写完整视觉与交互规格，并生成大型 HTML；首轮改为三个方向可减少一个候选，但仍须保证三个方向真正不同。
4. 阶段 4–7 对预览源码、状态、设计 draft、实现契约和最终规范多次读写。用户反馈越多，重复上下文和生成量越大。阶段 5 的页面建议规模保持不变。

### 持续设计

已有系统新增页面或组件本来可直接进入阶段 5/6，但仍先加载完整入口指令。此路径真正需要的是当前权威设计来源、目标页面或组件、相关状态规则及本次预览要求。它因此最能从入口路由和按需读取中受益。重复写入已有设计事实、状态与完整文档也会增加后续轮次成本。

## 建议改动

### 1. 缩短入口，按当前入口与阶段加载细则

`SKILL.md` 只保留任务识别、项目与端目录边界、状态恢复、安全写入、用户决策与批准门槛、当前阶段的阅读路由。阶段细则和较长模板移入对应的参考文件；首次设计、已有系统接入和完成后扩展分别路由。跨阶段不变量只保留一份，阶段文件写差异，不重复整套规则。

这会直接减少持续设计任务加载无关阶段的内容。完整首次设计最终仍可能读取大多数阶段文件，因此不能把移走的字节数直接算作总 Token 节省。需要检查路由是否漏掉语言、已锁定决定、设计来源和旧产物保护等不变量。

### 2. 参考收集由证据缺口驱动

阶段 2 先判断现有资料是否足以约束视觉方向：产品与用户、偏好与禁忌、颜色/字体/布局线索，以及可核实的参考来源。只补缺失的类别，不再为了凑固定数量搜集与当前决策无关的例子。信息稀少、参考矛盾或用户希望广泛探索时，继续使用现有 5–10 个参考的深度。

批准门槛仍在；用户的明确偏好继续作为方向生成的硬约束。质量风险是过早认定资料充足，因此产物须写明方向所依据的证据和未解决的偏好冲突。

### 3. 首轮三个完整方向

阶段 3 固定首轮三个方向。每个方向继续呈现完整色板、语义 token、字体、布局、标志动作和可比较的预览；布局差异要求与用户选择门槛不变。用户全部拒绝时，沿现有失败处理重新收集证据或调整定义，再生成新的三个方向。

这减少一个候选时的研究、说明与 HTML 生成量，但不减少单个候选的内容。潜在代价是少一个探索角度，须核对三个方向是否覆盖最重要的产品取舍。

### 4. 减少重复生成，保留同样交付

- 阶段 1/2 的文档仍落盘并获批；对话默认显示摘要、变化、待确认事项和文件链接，按需展示全文。
- 状态文件只保留恢复所需的当前阶段、设计来源、已锁定与待决决定、真实产物路径；避免把未适用的占位清单反复写入。修改时与 `doctor.mjs` 的实际检查条件保持一致。
- 最终 `DESIGN.md` 以持续维护的 `DESIGN.draft.md` 为基础补齐和固化，避免从预览源码重新推导或把已批准的内容整篇重写。
- 页面修改遵守现有的“只更新受影响页面/契约”规则；不改变阶段 5 的页面建议数量和状态要求。

### 5. 小范围试验方向页生成器

可以试验让脚本生成重复的方向卡框架、说明徽标、色板和响应式容器；模型仍负责三个方向各自的设计主张、完整规格、独特布局、预览内容与动效。这样有机会减少模型生成的重复 HTML，也避免为每个任务把整份结构模板写进上下文。

此项先做试验，不预先承诺纳入正式流程。若生成器使三个方向趋同、限制布局表达，或维护成本超过节省，应舍弃。展示案例 `docs/case/` 也应标为展示资产，避免被当作必读指令加载。

## 实施与验证顺序

1. **建立可比基线**：用相同模型、输入、预设反馈和交付范围，分别完成一次首次设计与一次持续设计；记录逐轮输入、输出和工具返回的 Token（平台有用量数据时以其为准）。记录产物与质量检查结果。
2. **先做指令与输出层改动**：入口路由、按证据收集参考、三个完整方向、摘要/差异确认和 draft 固化；不同时引入方向页生成器。复跑两类任务，检查总 Token 与每一项交付。
3. **必要时试验生成器**：若首次设计仍主要耗在方向 HTML，再单独试验脚本。用同样任务比较三个方向的布局差异、预览可运行性和实际 Token。

每次对照至少检查：首次设计的三个完整且不同的方向、阶段 5 既定页面集合、可运行预览、获批 `DESIGN.md`；持续设计对既有来源的复用、目标页面或组件的状态与预览、必要的设计规范更新；两类任务都能从 `state.md` 恢复。批准仍由用户作出。实测后判断是否保留改动，不预设节省百分比；如果某项节省伴随质量退步，只撤回该项。
