# zero-to-design · 交互式从 0 到 1 设计流程

这是为后端工程师和非设计师准备的交互式设计引导 skill。通过多轮对话和 7 个阶段（其中 2 个可选），把模糊的产品想法变成可执行的 `DESIGN.md`、页面设计预览和动效约束。

**核心原则**：不要假设用户懂设计。每一步都解释“为什么”，并给出具体的选择。

**全局规则：匹配用户语言（强制）**

- 以用户第一条消息的语言贯穿对话、问题、反馈示例、所有文档和预览中的可见文字。文档的章节标题、表头、字段名和说明，页面的标题、提示、按钮及演示区名称都须一致；`01-product.md`、`02-references.md`、`DESIGN.md` 和 `docs/prototype/design/state.md` 也不例外。
- 文件名、目录名、CSS 自定义属性、token、代码标识符、组件库和字体家族名保留英文。同一产物不混用界面语言；中文文档不用 `Product Definition`、`Core Palette` 等英文标题。

## 内部设计能力

本 skill 的设计约束随目录分发，不扫描或要求安装其他设计 skill。各阶段只读取当前任务需要的内部参考文件；用户明确指定其他 skill 时，可在不覆盖已锁定决策的前提下额外使用。

| 阶段 | 按需读取的内部能力 | 用途 |
|-------|------------------|------|
| 阶段 3 方向探索 | [shape](references/shape.md)、[bolder](references/bolder.md)、[critique](references/critique.md) | 明确方向主张、拉开差异、评审候选 |
| 阶段 4 首屏 | [typeset](references/typeset.md)、[layout](references/layout.md)、[adapt](references/adapt.md)、[delight](references/delight.md) | 在已选方向内细化首屏并核对 Web/H5 关键工艺 |
| 阶段 5 核心页面扩展 | [typeset](references/typeset.md)、[layout](references/layout.md)、[adapt](references/adapt.md)、[clarify](references/clarify.md) | 扩展页面、状态和复用组件，核对关键工艺与跨页一致性 |
| 阶段 6 跨页面打磨 | [clarify](references/clarify.md)、[colorize](references/colorize.md)、[typeset](references/typeset.md)、[layout](references/layout.md)、[harden](references/harden.md)、[adapt](references/adapt.md)、[animate](references/animate.md)、[audit](references/audit.md) | 按用户选择的维度检查和修改 |
| 阶段 7 设计系统 | [audit](references/audit.md)、[clarify](references/clarify.md) | 核对实现约束和文案规则 |

原生平台的排版、布局、适配、动效和审查还需按目标平台读取 [iOS](references/native/ios.md)、[Android](references/native/android.md)、[原生适配](references/native/adapt.native.md) 或 [原生审查](references/native/audit.native.md)。

**Node.js 辅助检查**：`<skill>` 代表本 `SKILL.md` 所在目录。`node <skill>/scripts/doctor.mjs --target <项目目录>` 检查 `docs/prototype/design/state.md` 与阶段产物；Web 源码的机械线索使用 `node <skill>/scripts/scan.mjs --target <文件或目录> [--scope type|layout|audit]`。两者均支持 `--json`。脚本不能替代对运行界面、原生应用和用户路径的观察。

以下负面约束与内部能力同时适用，不负责推导正面设计方向。用户明确要求优先；没有明确要求时，已核实的现有设计资产优先；其余字体和视觉选择来自产品定义与参考。

- **字体禁忌**：不用 Inter、Roboto、Arial、DM Sans、DM Serif、Plus Jakarta Sans、Outfit、Space Grotesk、Space Mono、IBM Plex（所有系列）、Fraunces、Instrument Serif、Playfair Display、Cormorant、Lora、Crimson、Newsreader、Syne
- **颜色禁忌**：不用紫蓝渐变背景；不用米白/骨白/米色背景搭配黄铜/陶土/深酒红色强调色的惯常“高端消费品”组合；不用霓虹光晕
- **布局禁忌**：不在每节上方都放 eyebrow；不用 01/02/03 编号章节标记、相同的三卡功能行、hero 指标模板、渐变文字或默认装饰性的玻璃拟态
- **文案禁忌**：不用 em dash；不用 “seamless”“elevate”“unleash”“empower”“next-gen” 或格言式三行排比
- **通用规则**：不用 Lorem Ipsum、纯黑 `#000000`、纯白 `#FFFFFF` 或没有实际用途的大面积装饰阴影

## 流程总览

```
入口 A：新产品            → 阶段 1
入口 B：已有系统          → 已有系统盘点 → 阶段 5 / 阶段 6
  ├─ 有可复用设计资产      → 读取并核对现有事实来源
  └─ 没有设计资产          → 探索系统 → 建立观察到的基线 docs/prototype/DESIGN.md

阶段 1：产品定义          → 01-product.md
阶段 2：收集设计参考      → 02-references.md
阶段 3：方向探索          → 03-directions.html + 用户选择
阶段 4：首屏预览迭代      → 按平台运行的 04-<screen>-v1 源码 → v2 → v3... + DESIGN.draft.md
阶段 5：核心页面扩展（可选）→ 按平台运行的 05-<screen>-v1 源码 + 页面地图 + 组件清单
阶段 6：跨页面打磨（可选）→ 打磨日志/评审 + 更新后的页面预览 + DESIGN.draft.md
阶段 7：设计系统          → docs/prototype/DESIGN.md + docs/prototype/design/tokens.css + docs/prototype/design/assets/
```

文件编号与阶段一致：阶段 N 的产物以 `0N-` 开头；阶段 7 的最终文档固定为项目根目录下的 `docs/prototype/DESIGN.md`，`tokens.css` 和资源仍放在 `docs/prototype/design/` 下。

**Web/H5 原型技术约束**：阶段 3 的 `03-directions.html` 只比较视觉方向。阶段 4 起使用目标项目的框架、组件库和样式生成可运行的 UI 原型；已有项目沿用现有技术栈与构建工具。新项目默认 Vue 3 + TypeScript + Vite，Web 使用 Ant Design Vue（`ant-design-vue`），H5 使用 Vant 4（`vant`）；用户明确指定的项目技术栈优先。只产出用户要求的端；同时设计 Web 和 H5 时，在 `docs/prototype/design/web/` 与 `docs/prototype/design/h5/` 分别设置预览入口，共用语义 tokens，但各自采用适合设备的组件、布局和交互。预览入口无需接入目标应用路由。原型使用示例数据和必要的本地交互状态，不接入真实 API 或业务状态管理。必要时可制作原型专用 UI 组件，并记录使用边界。原生平台不适用上述 Web/H5 默认技术栈。

## 入口解析与项目范围

读取 `docs/prototype/design/state.md`、检查源码或创建产物**之前**，先确定用户意图与项目范围。项目范围是本 skill 允许读写设计文件的仓库或应用。

1. **明确意图优先。** 用户已经说清是新产品、重设计、已有应用新增页面/组件、继续上次流程，还是重新开始，就直接采用。明确的“从头开始”“重新开始”“完整重设计”优先于自动恢复状态；不要让用户重复选择模式。
2. **当前目录明确时直接使用。** 如果请求指向当前项目，且工作目录明显是目标项目，直接使用并告知用户范围，不再重复询问路径。
3. **只有模式不清时才提问。** 对“帮我设计这个”这类泛化请求，用用户语言提出一个聚焦问题：这是从零创建产品、在已有项目中设计页面/组件，还是继续上次流程？
4. **区分本地范围与运行时证据。** 明确的本地项目路径决定可读写范围；运行 URL 仅用于检查运行界面。如果路径和 URL 指向不同应用，URL 只作运行时证据，产物仍写入明确指定的本地项目。用户只提供 URL、且当前目录明显不是对应项目时，读取源码或创建产物前先询问本地项目目录。不要读一个应用，却把产物写到无关目录。
5. **仅在目录不清时确认。** 两种入口都优先使用本地项目目录；只有运行时 UI 检查能增加证据时，才请求运行 URL。
6. **恢复状态前先保证重启安全。** 简要说明选定的入口模式、本地项目目录及可选运行 URL。用户明确要求重新开始或完整重设计、且已有 `docs/prototype/design/state.md` 时，不恢复或覆盖旧状态。默认创建 `<project>/design-restarts/<YYYYMMDD-HHmmss>/`；用户指定其他工作区则按其路径。在重启工作区中，本 skill 的相对产物路径都以该工作区为根，新的状态文件为 `<workspace>/docs/prototype/design/state.md`，其他产物也在 `<workspace>/docs/prototype/design/`。可检查原项目作为实现参考，但只在已确定的工作区写入。若用户选择在原项目继续，先把原有 `docs/prototype/design/` 非破坏性复制到获批的备份/归档路径，核实备份存在，再写新产物。其他情况下，在已确定项目中检查 `docs/prototype/design/state.md`，适用时恢复。明确的本地路径优先于当前目录；URL 永远不是写入范围。

不要让用户分别回答已经明确的模式和位置。项目目录未确定前，不检查或创建设计产物。

## 入口模式

进入阶段 1 前先确定入口模式。用户要在已有系统中新增页面或组件时，不要强行让其回答从零设计产品的问题。

### 入口 A：新产品

产品是新的，或没有已有应用作为范围时，走正常流程。对已有产品进行完整重设计也属于重新开始；先按重启安全规则保留旧状态并确定新的设计工作区，再进入阶段 1。

### 入口 B：已有系统

用户已有仓库、运行应用或稳定 UI，并希望新增页面或组件时使用。先按入口解析确定项目目录，再检查系统，然后才做视觉决策。目标页面/组件来自用户请求；只有不明确时才询问。运行 URL 是可选证据，不是本地检查的前提。

先区分两种情况：

1. **已有设计资产。** 搜索 `DESIGN.md`、`design-system.md`、token 文件、主题文件、组件文档和项目级代理指令。用户指定的事实来源，经与运行实现核对后应视为权威。阅读相关路由、全局样式、tokens 和复用组件。不要仅因文件不在 `docs/prototype/design/` 下就再造一套设计系统。
2. **没有可用设计资产。** 探索仓库，可能时也检查运行应用。检查路由、布局、代表性页面、全局 CSS、主题变量、字体导入、基础组件、响应式断点、交互状态以及加载/空/错误状态。以观察到的实现为证据，不发明新视觉方向。生成基线设计系统文档，记录观察到的规则、源码路径、信心程度、尚未解决的不一致和安全扩展规则。

进入阶段 5 前，已有系统盘点必须生成或确定这些产物。除非用户明确选择其他位置，新产物放在 `docs/prototype/design/` 下：

- `docs/prototype/design/existing-system.md`：系统范围、技术与组件库、现有路由、视觉语言、响应式行为、无障碍基线和事实来源路径
- `docs/prototype/design/component-inventory.md`：可复用组件与基础元素；每个目标标记为 `reuse`、`extend` 或 `new`
- `DESIGN.md` 或现有等效文件：权威设计系统来源；若由探索生成，保存到项目根目录下的 `docs/prototype/DESIGN.md`，标为“观察到的基线”，并保留指向源码的证据链接
- `docs/prototype/design/state.md`：记录 `Entry Mode: existing-system`、权威来源路径、探索状态和目标页面

盘点后，新增核心页面或多页面扩展直接进入阶段 5；单个现有页面的窄范围打磨直接进入阶段 6，并只执行相关打磨项。除非用户要求新视觉方向或完整重设计，否则不需要阶段 1–4。

### 已有系统的事实来源规则

- 优先使用仓库真实的事实来源：已有 tokens 优于重写的 tokens，已有组件优于静态模拟；页面导航以现有实现为证据。
- 保持现有技术栈、组件库、构建工具和渲染方式。Nuxt/Vue 系统使用 Vue/Nuxt 原型，React 系统使用 React 原型；不要为适配新项目默认方案而迁移已有项目。
- 在 `docs/prototype/design/existing-system.md` 和当前权威设计来源中，区分观察事实、推断规则和拟议改动。
- 系统已有不一致时，记录不一致，并为目标页面选择局部扩展规则；不要悄悄统一整个产品。
- 只有组件清单解释了为什么复用或扩展不足时，新页面才可以引入 token 或组件。
- 未获用户明确批准，不覆盖或移动已有设计资产。权威来源在 `docs/prototype/design/` 外时，从 `docs/prototype/design/state.md` 和生成产物引用它。
- 应用无法运行时继续静态检查，并标记运行时观察不可用；不要声称已验证运行行为。

每个阶段完成后，如果当前产物可信度高（没有歧义或缺项，用户反馈明确），可直接进入下一阶段，无须问“要进入下一阶段吗？”阶段 1 和 2 须先按各自的批准门槛取得产物确认。

**必须向用户确认的情况：**阶段 1 的 `01-product.md` 和阶段 2 的 `02-references.md` 尚未获批；回答含糊或推断不确定；当前阶段仍有未解决问题；涉及不可逆决策，例如最终批准 `DESIGN.md`。

**不必再确认的情况：**阶段 1 和 2 的产物已获用户确认，无须另问是否进入下一阶段；阶段 3 已生成方向页，正在等待用户选择；阶段 4 的每轮修改都需要反馈，但用户说“可以了”后直接进入分流决策。

进入下一阶段且信息明确时，用一句话说明即可，不必提出冗长的过渡确认问题。

**全局规则：不要跨阶段补问**

- 每个阶段只问本阶段的问题，不要返回补问前一阶段的问题。
- 用户跳过前一阶段的问题时，代理应根据现有信息推断，并在对应文档标记为 `agent-inferred`。
- 后续阶段只能阅读前一阶段的产物，不得重问本应由前一阶段收集的信息。

**全局规则：跨会话恢复**

- 确定项目范围后，除非用户明确要求重新开始，第一项文件操作必须检查并读取目标项目的 `docs/prototype/design/state.md`（若存在）。不要读取未确定目录或其他项目的状态文件。
- 存在状态且未要求重启：从 `Current Phase` 恢复，简要告知已完成内容及下一步；不得重跑已完成阶段、再次提出 `Rejected Directions` 中的方向，或违反 `Decisions Locked`。
- 明确要求重启或完整重设计，且状态已存在：保留旧状态，不自动恢复或覆盖；先建立入口解析规定的重启工作区或已验证备份/归档，再开始阶段 1。使用独立工作区时，状态和各阶段产物都写在其中，不能悄悄写回原项目的 `docs/prototype/design/`。
- 没有状态：已有系统先做上述盘点并创建 `docs/prototype/design/state.md`；新产品进入阶段 1。

**全局规则：完成后的扩展模式**

- `docs/prototype/design/state.md` 已标为 `status: complete`，用户后来要求新页面或组件时，进入扩展模式，不重启全流程：
  1. 读取 `docs/prototype/design/state.md` 中记录的权威设计来源，将其作为唯一约束来源。新生成的文档位于 `docs/prototype/DESIGN.md`；已有系统的权威来源也可能位于其他路径，不能按默认路径猜测。
  2. 遵循阶段 5 的 UI 契约及阶段 6 的相关打磨项，一次处理一个目标，并创建对应平台的 `06-<target>-v*` 预览源码。页面应有 default/loading/empty/error 状态；组件应有相关状态与变体矩阵。
  3. 用户反馈涉及设计系统级规则（例如所有页面的卡片圆角都应更大）时，更新状态文件记录的权威来源，并记下原因和用户原话。若来源是生成的 `DESIGN.md`，递增版本号（如 v1.0 → v1.1）；否则遵循该来源既有的版本约定。
  4. 新页面或组件获批后，将其加入 `docs/prototype/design/state.md` 的 `File Checklist`。
- 扩展模式不重跑阶段 1–4；产品定义、方向和首屏已经锁定。
- 只有用户要求完整重设计（新方向或新风格）时，才启用重启安全流程，保留旧状态并建立新的工作区或已验证备份/归档。不得原地重置或覆盖旧状态。

## 阶段 1：产品定义

**目标**：通过 8 个关键问题，明确“要做什么”和“应该给人什么感觉”。

**执行方式**：在对话中逐步提问。推荐一次问一个，也可以一次问 3–4 个以提高回答效率；根据用户答案的详细程度调整。

**开放输入规则（必须遵守）：**

- 每题给出的选项只是帮助用户回答的提示，不是封闭的单选题。
- 每题都要明确允许用户用自己的话回答，例如在选项后补充“也可以直接描述你的想法”。
- 用户自己给出的答案与列出的选项同样有效，直接写进 `01-product.md`；不要强制归入某个预设选项。
- 用户已用自己的话描述时，不要反问“这算专业感还是创造感？”；原话比预设标签更准确。应复述并记录其描述。

**智能跳过**：用户最初或后续回答已明确覆盖的问题，不再重复询问，只需确认。只有回答清楚且无歧义时才跳过；“做得好看一点”仍需追问。

**提问呈现规则（必须遵守）：**

- 下方 0–7 仅是内部索引，不能向用户展示。实际提问从 Q1 起连续编号，不能有缺号。
- 已知信息放在不编号的确认区，与待答问题分开。不要让确认区和问题清单使用两套混乱的编号。
- 例如用户已说明“卖数字产品的网站”和“首页有推广及商品列表”，可先确认产品类型与浏览/购买目标，再只问尚不明确的产品名、用户、氛围等。

**缺失信息规则：**

- 用户明确跳过或未回答某项必答问题时，不要进入后续阶段再返回补问。
- 在阶段 1 内根据已有答案推断，写入 `01-product.md` 并标记 `agent-inferred`。例如独立创作者的数字商品平台可推断“温暖 + 专业”，B2B API 市场可推断“信任 + 高效”。
- 若对推断没有把握，在结束阶段 1 前只确认一次；不要拖到阶段 3。

**必答问题（按顺序；编号仅供内部使用）：**

0. **产品名称**：产品叫什么？后续设计文件会使用此名称。
1. **一句话产品定义**：用自己的话，而非正式口号，说明这是什么。
2. **典型目标用户**：最典型的一位用户是谁？其年龄、职业以及目前如何赚钱或销售？
3. **用户心理状态**：打开页面前，用户带着什么期待或情绪？例如好奇、怀疑、找工具、受人推荐。
4. **氛围**：界面最应传达哪 1–2 种感受？可从信任、高效、平静、兴奋、专业、温暖、轻松有趣、创造力中选，也可以自己描述。选项只用于解释含义：信任意味着可靠，效率意味着不浪费时间，平静意味着专注，兴奋意味着探索欲，专业意味着严谨，温暖意味着有人情味，轻松有趣意味着不那么严肃，创造力意味着独特且启发灵感。
5. **核心差异点**：与主要竞争者相比，最重要的一个区别是什么？只选最重要的一项。
6. **转化目标**：最希望用户在此页面完成什么动作？例如注册、下载、购买。
7. **设计约束**：
   - 平台：Web、H5、Web + H5、iOS、Android 还是 Desktop？只设计用户要求的端。H5 记录目标手机画布；iOS/Android 还必须记录设备形态（phone 或 tablet）。如果用户只说 iOS、Android 或“移动端”，追问一次是 H5 还是原生应用，以及主要设备形态；不能在阶段 1 结束时仍缺少形态。
   - 目标用户年龄段
   - 无障碍需求：例如色盲友好、屏幕阅读器、大字模式
   - 已有品牌资产：logo、颜色或字体（如有，请用户提供）

**按答案质量决定是否追问：**

- “和竞争者差不多” → 追问用户为何会选择这个产品。
- “受众很广” → 追问只能服务一种人时会选谁。
- “要好看” → 追问希望用户因此感到专业、可信、有趣、高级，还是其他感受。
- 心理状态含糊 → 追问用户第一次听到产品时，更可能觉得“我需要它”还是“这是做什么的”。

**产物**：在项目根目录创建 `docs/prototype/design/01-product.md`，包含产品名称、一句话定义、目标用户、用户心理预期、氛围关键词、核心差异点、转化目标、设计约束和阶段 3/4 的关键页面。所有标题与字段名都使用用户语言（中文示例：`产品定义`、`产品名称`、`一句话定义`、`目标用户`、`用户心理预期`、`氛围关键词`、`核心差异点`、`转化目标`、`设计约束`）。

**批准门槛**：8 个必答问题都有明确答案（用户回答或代理推断，推断需标记），且用户明确确认 1 或 2 个关键页面。两项均满足后，在 `docs/prototype/design/state.md` 和 `01-product.md` 记录页面，创建尚不存在的 `01-product.md`。向用户展示完整 `01-product.md` 的文件入口和简短摘要，供其核对；根据反馈修改同一文件，直到用户明确确认整份产物，再进入阶段 2。产物获批后无须另问“要进入阶段 2 吗？”

**阶段 1 → 阶段 2 的页面交接**：8 项完成后，提议阶段 3/4 应一起设计哪 1–2 个最重要页面。大多数产品先做 **1 个关键页面**；仅当两个页面紧密耦合、必须一起看才能判断设计语言时（例如聊天列表 + 聊天详情、商店首页 + 商品详情、卡片信息流 + 个人主页），才提议 2 个。询问用户是否接受或想换页面；最多 2 个。用户只选 1 个时，不得暗自加第 2 个。

## 阶段 2：收集设计参考

**目标**：让用户从“不知道想要什么”走到“知道喜欢什么、不喜欢什么”。

**执行方式：**

1. **先邀请用户推荐**：询问用户是否有想参考的竞品或其他产品；用户可以提供名称、链接、截图或具体页面，最好说明想借鉴或避免什么，也可以直接跳过。代理核实其产品、页面和目标平台，分析可借鉴点与不适用点；只有名称时由代理查找。无法核实时请用户补充线索，暂不计入最终参考清单或有效反馈。用户推荐先作为候选，不能直接当作设计要求。

2. **代理补齐推荐**：根据阶段 1 的产品定义和用户推荐，整理共 5–10 个参考供用户筛选。核实后入选的用户产品按类别占用同类或跨品类名额，代理补齐不足的数量；未入选的候选也记录原因。**参考类型须与阶段 1 确定的平台匹配**：
   - **移动端或原生应用**：推荐真实移动应用（App Store / Play Store / 官方落地页）及移动应用截图集合，不要默认推荐桌面网站。
   - **Web 或桌面产品**：推荐网站及以 Web 为主的设计图集。
   - **所有平台**都要覆盖下列四类；字体灵感库不是可选项。最终清单中的每项参考必须给出可直接访问的域名、商店链接或具体页面 URL，不能让用户自行搜索：
     - 2–3 个同类产品（直接竞争者）
     - 2–3 个气质相近的跨品类产品或体验
     - 2–3 个适合目标平台的设计灵感图库
     - **1–2 个字体灵感库，单独列出**：如 Typewolf、Font Pair、Fontshare；说明用途，例如看真实字体搭配或找可免费商用的字体。配色工具如 Coolors 可另列，不能充当字体灵感库。

   下表仅供选取候选；最终每项都附可直接访问的页面或商店链接。移动应用还须提供应用商店或移动截图来源，不能只给桌面版营销网站。

3. **向用户收集截图和整体感受**：请用户打开最终参考清单，分别回答两层问题；用户已说明具体借鉴或避免点的，不要重复追问：
   - **整体层面**：这个应用/网站/体验整体给人什么感觉（专业、温暖、大胆、平静、活跃、高级、亲近或其他）？希望自己的产品借鉴其中哪部分？有哪些整体气质明确不想要？
   - **具体截图层面**：截取 1–2 个喜欢或不喜欢的页面/局部，并说明具体原因（颜色、字体、布局、动效、文案、间距、图像风格等）。

4. **提供快捷路径（用户没时间逐个查看时）**：明确提供下面两种自然语言回答方式，**不要**额外追加 A/B/C 字母选项：

   > 如果没时间逐个看，可以直接用自己的话回复：
   > - “直接继续”——我会从同类产品的共同气质推断审美边界，整理参考文档供你核对；你确认后再进入阶段 3 生成方向。
   > - 或先说出明确偏好，再说“直接继续”。例如：“不要红、蓝、紫或渐变；用衬线字体。直接继续。”也可以说：“干净的黑白底，加少量亮色点缀。直接继续。”

   不要在这段说明后再添加“A. 查看网站 / B. 快捷继续 / C. 让我推断”等选项。用户应直接用自然语言回答。用户明确说出的“必须保留／必须避免”等偏好，无论来自正常反馈还是快捷路径，都按原话写入 `02-references.md` 的“明确偏好”；阶段 3 将其视为**硬约束**。推荐产品本身不是硬约束。

5. **整理文档**：把用户推荐的候选、核实与筛选结果、代理补充的参考、用户截图、整体感受、局部标注和明确偏好写入 `02-references.md`。

## 阶段 3：方向探索

**目标**：依据产品定义、参考资料及阶段 1 确认的 1–2 个关键页面，让用户从 3–4 个**真正不同**的设计方向中选择。

**前置条件**：`01-product.md` 和 `02-references.md` 已存在，`docs/prototype/design/state.md` 已记录 1 或 2 个关键页面。阶段 3 不再追问氛围、目标用户、核心差异点等产品定义问题。即使 `01-product.md` 某些字段为空或标记为 `agent-inferred`，也直接依据现有推断生成方向，不让用户补填。

**关键要求：**

- 按内部 [shape](references/shape.md)、[bolder](references/bolder.md)、[critique](references/critique.md) 规则推导、拉开和评审方向，不重复收集阶段 1/2 已记录的信息。
- 3–4 个方向须沿着**与该产品有关**的轴线拉开差异，由阶段 1/2 动态推导，而不是套用固定列表。可能的轴线包括暖/冷色、衬线/无衬线、简约/丰富、明/暗、编辑式/工具式、卡片网格/列表信息流。判断核心是：哪些轴线最能呈现该产品的气质取舍？
- 每个方向都是完整的设计语言，不能只是同一布局换配色。
- **交互术语适配平台**：阶段 1 的平台决定交互描述、状态名称和动效触发方式。移动触控使用 tap、press、active、long-press、swipe 和触控热区；Web/桌面使用 hover、click、focus、active。HTML 预览可为了桌面查看方便而提供 hover，但书面规范须说明平台真实的输入方式。

**执行方式：**

1. **读取本阶段内部能力。** 按 [shape](references/shape.md) 从 `01-product.md`、`02-references.md` 和已确认的关键页面提炼设计张力；按 [bolder](references/bolder.md) 拉开候选差异；生成后按 [critique](references/critique.md) 检查方向是否服务产品。无需扫描或询问用户选择外部 skill。

2. **记录约束来源。** 在 `docs/prototype/design/state.md` 记录已使用的内部能力及用户明确指定的额外 skill。用户的明确偏好和已锁定决策始终优先。

3. **生成方向文件**：创建 `docs/prototype/design/03-directions.html`。`templates/directions-template.html` **只能**作为页面结构骨架（顶部产品分析卡及方向列表框架）；其中颜色、字体、间距和视觉效果都是占位示例，必须用 `01-product.md` 和 `02-references.md` 推导出的值全部替换。不要把模板的默认暗色外观当作方向或起点。模板中可见标题、提示、页脚说明和按钮文案也必须翻译成用户语言。每个方向的具体内容都须在当前轮次重新推导。文件包含：

   - 顶部产品分析卡：一句话产品定义、目标用户、核心场景。
   - 3–4 个方向：桌面端**两列网格，每行最多两个**；移动端单列。不能把所有方向排在同一行，让桌面 mini mockup 被挤成手机宽度。
   - **mini mockup 比例与阶段 1 记录的平台和设备形态一致**：Web/桌面用横向桌面比例，手机用竖向手机比例，平板用平板比例。同时设计 Web 和 H5 时，每个方向分别展示两端的小型画布，仍只用于轻量方向比较。不得用平板或横向画框装手机界面。形态仍有歧义时，在生成前确认；预览区太窄时减少每行方向数，不能把桌面界面硬缩成手机画框。
   - 每个方向须包含：
     - **名称**：用用户语言写两个有画面感的词，例如“明亮工作台”“纸页目录”。
     - **一句话主张**：描述感受，不列功能。
     - **理由**：说明为何适合产品，引用阶段 1 的氛围和核心差异，或阶段 2 的参考气质。
     - **色彩系统**：分为核心色板（3–4 个背景、文字、强调色）与 UI 语义 tokens（3–6 个卡片底色、边框、次要文字、成功/警告/错误、徽章底色等）；每个 token 有如 `surface-card`、`border-subtle`、`text-secondary` 的角色标签。
     - **字体系统**：明确字体名称、字重、字号/行高；例如 `Display: "ZCOOL XiaoWei" 600 48px/1.2`。至少有 Display、Body、Mono/Accent 层级，并解释各自用途。
     - **布局模式**：明确描述目标界面的关键区域，而非让用户只看小预览猜。区域由页面类型决定：主页可能是 Hero + 列表，仪表盘可能是侧边栏 + 数据区，落地页可能是 Hero + 卖点。每个区域说明位置与比例（如左 40% 放大标题和搜索、右 60% 放预览网格）、内部信息层级（列数、卡片信息、筛选 chips）、区域间视觉权重，并用一句话概括布局策略。
     - **带动画的标志动作演示**：用 2–4 句解释动作、方向依据及适用位置，并用真实 CSS 动画或过渡演示。示例：“卡片呼吸”让卡片在 hover（Web）或 press（移动端）时上移 4px、阴影由 1px 扩到 12px；mini mockup 中的精选卡片要实际响应。
     - **小型界面预览**：真实体现所述布局、颜色、字体和标志动作，包含足以判断布局是否成立的关键元素。

   **预览页面数**：状态文件记录 2 个关键页面时，每个方向都要把两页**上下堆叠**显示，各占方向卡片全宽，并在上方标明页面名；不能左右并排导致过窄。只记录 1 页时就只展示 1 页，不得擅自加第二页。

   **关键元素由代理根据阶段 1 的产品定义和界面类型判断**，不是固定清单。需问：打开界面完成核心动作时必须看见哪些入口或信息？转化路径上不可缺哪些 UI？缺少它们还能判断布局吗？例如数字商品首页通常需要导航（logo、主要导航、登录入口）、Hero（标题、CTA）、搜索、分类筛选和至少 4 张商品卡；仪表盘可能是侧边栏、数据卡和图表；单页作品集可能只需导航、Hero、作品网格。

   常见问题与修正：
   - ❌ 预览只有 1–2 张卡片，无法判断多卡片排布。✅ 至少展示 4 张，呈现网格密度和间距。
   - ❌ 缺少搜索框或分类入口，用户无法判断入口样式。✅ 对确实需要它们的产品，在导航或 Hero 中展示搜索、分类 chips 和登录按钮。
   - ❌ 不管产品类型都塞搜索和筛选。✅ 先依据转化路径确定必需元素；作品集未必需要搜索。
   - ❌ 只有独立演示区的卡片会动。✅ mini mockup 中的商品卡复用同一 CSS class，同样响应 hover/press。
   - ❌ 标志动作只有“Highlighter Mark”标题。✅ 标题后紧接 2–4 句说明动作、用途及其与方向的关系。

4. **打开预览**：使用当前环境可用的文件预览或浏览器工具展示 `03-directions.html`；若无法打开，给用户可访问的绝对路径并说明未完成视觉核对。

5. **引导用户选择**：展示全部 3–4 个方向后，按两层结构引导：
   - **已有满意方向**：可回复实际展示的 A/B/C（有第四个时也可选 D），或按元素组合。可细到颜色、字体、布局和动效，例如“A 的按钮颜色 + B 的字体 + C 的布局”；仅展示了三个方向时，不提 D。
   - **仍不满意**：可整体拒绝并描述想更暖、更专业或更大胆；也可局部反馈，例如“A 的颜色好，但字体太冷，换暖一点再生成”“B 的布局可用，但标志动作太花，简化后重做”。
   - 向用户说明这些是用于快速感受颜色、字体、布局和动效的**方向草案**；选定后，阶段 4 才生成更完整真实的整页预览。

**方向生成规则（必须动态推导，不能套模板）：**

- **标志动作必须可感知**：在 `03-directions.html` 中用真实 CSS 动画、hover/press 过渡或滚动显现演示，不能只给文字标签；mini mockup 内的对应元素也须响应。
- **预览元素不能引入额外抢眼色相**：商品卡、图片、图标等占位元素使用设计系统颜色或中性色，不用随机的高饱和绿/蓝/橙。若强调色是红色，却出现大片绿色商品卡，会误导用户。图片区域用低饱和中性色或真实商品图；强调色只用于标签、价格、按钮等位置。
- **HTML 中的信息层级必须清楚**：每个方向的“理由”“色彩系统”（其下有核心色板、UI 语义 tokens）“字体系统”“布局模式”“标志动作”“界面预览”标题与内容应明显分层。标题可用至少 13px、明显大于正文的粗体和该方向强调色或深灰色；与上文至少间隔 24px、与下文间隔 12–16px；内容块可缩进 16–24px 或用浅底区分。核心色板和语义 tokens 必须明显归属于色彩系统。
- **每个技术章节标题都有 `i` 解释徽标**：在右侧放 ⓘ 或小写 i，hover 时显示简短说明。目标用户是后端工程师或非设计师，不能假设他们理解术语。tooltip 须解释章节和关键词：
  - 理由：根据阶段 1 的产品定义和阶段 2 的参考气质，解释方向适合产品的原因。
  - 核心色板：决定整体感受的 3–4 个主色；`bg-page` 是页面背景，`text-primary` 是主要文字，`accent` 用于按钮、价格与重点。
  - UI 语义 tokens：按 UI 用途而非色相命名；`surface-card` 是卡片底色，`border-subtle` 是浅边框，`text-secondary` 是次要说明，`badge-bg` 是标签底色。
  - 字体系统：Display 是大标题字体，Body 是正文字体，Mono 是常用于价格、代码和标签的等宽字体。
  - 布局模式：关键区域如何排列；Hero 是首屏主视觉区，CTA 是引导行动的按钮区，列表区展示商品或内容。
  - 标志动作：此方向最有记忆点的微交互；提示用户在 Web 上 hover/click 或在移动端 tap/press。
  - 界面预览：使用真实颜色、字体和布局构成的小型界面，帮助用户判断方向的实际样子。
  - tooltip 仅用 CSS，不依赖外部库；徽标使用方向强调色或灰色，提示底色用该方向卡片底色、文字用正文色，确保可读。

**所有方向必须从 `01-product.md` 和 `02-references.md` 推导**，不能固定塞进“午夜/暗色/工业风”。推导顺序：

1. **读阶段 1，确定核心张力**：产品类型和目标用户决定方向是否符合品类；氛围关键词决定气质；核心差异点决定记忆点；转化目标决定功能重点。
2. **读阶段 2，确定审美边界**：把入选的用户推荐与代理推荐一起作为参考来源；推荐产品本身不是硬约束。`02-references.md` 的“明确偏好”中用户原话是硬约束，必须逐条落实。禁用色不得出现在任何方向；指定色至少要出现在安全方向和贴近参考方向；衬线等字体偏好直接影响各方向选型。至少一个方向靠近用户明确喜欢的气质；所有方向避开明确拒绝的元素；参考的整体印象决定“熟悉感与突破感”的比例。
3. **按角色选择方向**：安全方向贴近用户偏好、风险低；大胆方向从核心差异点出发形成视觉突破和强记忆点；贴近参考方向最接近阶段 2 的参考气质；反向方向与主流参考气质形成对照。生成四个时覆盖四种角色；生成三个时选择最能呈现产品取舍的三种，并在状态文件说明省略原因。
4. **布局差异是硬要求**：3–4 个方向至少包含 **2 种结构不同的布局**，区域组成或信息层级必须不同；大胆方向的突破须包含布局。例如同一主页可以是居中 Hero + 商品网格、侧边导航 + 密集数据带，或编辑式杂志排版。若都是相同的导航/Hero/网格骨架，应重新生成。
5. **名称来自真实设计语言**，不用固定词库。“明亮工作台”“纸页目录”能表达材质和气质；“现代简约版”“默认方案”只是描述，不算方向名。

错误示例：无论产品是什么都给大胆方向安排“午夜仓库 / 暗色 / 工业风”。正确做法：创作者数字商品平台可依据阶段 1/2 的信息，生成“纸页目录”等贴合产品的方向。

**产物**：`docs/prototype/design/03-directions.html`。

**批准门槛**：用户明确选中一个方向，或提出元素组合指令。

## 阶段 4：首屏预览迭代

**目标**：把已选方向落实成第一个关键界面的真实设计预览，反复迭代直到用户满意。

**首屏由阶段 1 决定**：阶段 1 末确认的 1–2 个页面就是首屏；可以是首页、仪表盘、落地页、核心功能页，或聊天列表 + 详情、商店首页 + 商品详情、卡片流 + 主页等紧密关联的一组。不要假设一定是“首页”，也不要擅自增加第二页。

**生成 v1 前再次核对关键页面**：简要复述 `docs/prototype/design/state.md` 中记录的页面，问用户是否仍正确。用户若想换页，不要立刻按新选择生成阶段 4 预览；应回到阶段 1 的页面交接，取得明确确认，更新 `docs/prototype/design/state.md` 和 `01-product.md`，重新生成 `03-directions.html`。由于新方向页展示的是新的页面组合，旧方向选择失效；必须让用户再次按阶段 3 门槛选方向，之后再进入阶段 4。

**关键要求：**

- 按内部 [typeset](references/typeset.md)、[layout](references/layout.md)、[delight](references/delight.md) 细化已选方向；Web/H5 还按 [adapt](references/adapt.md) 核对实际触控与焦点。只读取本轮实际需要的文件。
- 生成 v1 前，核对目标项目的框架、构建工具、组件库、可复用 UI 组件和主题入口；新项目采用上述 Web/H5 默认技术栈。把实际选择和预览运行方式写入 `docs/prototype/design/state.md`，并带入 `DESIGN.draft.md`。
- Web/H5 在 `docs/prototype/design/<platform>/` 建立独立预览入口，使用对应组件库和项目样式，并把共用语义 tokens 映射到各端主题。新项目可由同一 Vite 原型工程运行两个入口；已有项目使用其现有构建工具。每轮保留带版本号的页面源码，入口指向当前版本，旧版本仍可复查。源码后缀沿用目标框架（Web/H5 新项目为 `.vue`）；原生平台沿用原有预览形式和 native 指引。
- 每次迭代创建新版本源码（v1、v2、v3……），绝不覆盖旧版本。使用可信的示例数据，不用 Lorem Ipsum；本地状态只用于演示 UI 交互。

**执行方式：**

1. **生成 v1**：
   - 确认 **1 个关键页面**时，在目标平台目录创建 `04-<screen>-v1` 页面源码；`<screen>` 是界面名称，如 `home`、`dashboard`、`landing`。新项目示例路径为 `docs/prototype/design/web/04-home-v1.vue` 或 `docs/prototype/design/h5/04-home-v1.vue`。
   - 确认 **2 个关键页面**时，为每端创建展示两页的 `04-<screen1>-<screen2>-v1` 页面源码。桌面可并排，移动端可上下堆叠或切换标签；每页都要有足够内容以判断布局，并能一起评估连续性。
   - **画布符合已记录的设备形态**：手机界面放在真实比例的竖向手机画框内，平板使用平板画框，Web/桌面使用横向桌面比例。不能把手机界面拉到整页桌面宽度，或塞进平板画框。
   - 界面包含哪些区域，要由代理根据阶段 1 产品定义和阶段 3 获选方向的布局模式动态推导，而不是套固定模板。判断用户打开界面要完成什么动作，哪些区域支持该动作。例如数字商品首页通常需要导航、Hero、商品列表、分类/搜索入口、CTA 和页脚；仪表盘可能需要侧边栏、数据卡与图表；单页作品集可能只需导航、Hero、作品网格与页脚。
   - 使用可信的商品名、价格、描述等示例数据，优先使用目标端的真实组件库组件；必要的自定义 UI 组件记录用途。提供符合平台的交互状态（Web：hover/active/focus；H5：tap/press/active），并保持颜色、字体、布局与已选方向一致。

2. **打开预览**：运行记录在状态文件中的预览命令，展示对应端的单屏或双屏页面，核对组件实际渲染、交互和目标画布。Web/H5 展示给用户前，检查关键排版、表面层次、图标对齐、实际点击区域与焦点；修正影响阅读或操作的问题，并在 `docs/prototype/design/state.md` 的工艺检查记录中写明发现、修正与暂留项。双端任务分别核对 Web 与 H5；原型入口不要求接入目标应用路由。

3. **用户反馈循环**：
   - 用户说“可以了” → 生成 `DESIGN.draft.md`，再进入步骤 5 的分流决策。
   - 用户说“修改 X” → 仅修改 X，生成 v2；其他内容保持不变。
   - 用户说“方向不对” → 回阶段 3，并记录拒绝原因。

4. **生成 `DESIGN.draft.md`**：首屏获批后立即从最终预览提取设计决策，生成 `docs/prototype/design/DESIGN.draft.md`。其结构应与最终 `DESIGN.md` 同构，使用阶段 7 的十章骨架，但内容先从已批准首屏提取，并标记为 draft。至少包括：核心色板和 UI 语义 tokens；字体家族、字重、字号、行高；布局、间距、圆角；目标端的框架、构建工具、组件库、预览入口和主题映射；已批准首屏的平台交互状态以及 loading/empty/error 规则。阶段 5 持续更新，阶段 6 记录验证过的打磨决策。

5. **分流决策（代理主动建议，用户决定）**：首屏获批且 draft 生成后，依据产品类型提出建议并等待用户确认：
   - **阶段 5 核心页面扩展**：产品还有其他核心界面时，把已选方向扩展到能验证关键用户路径的最小页面集合。
   - **阶段 6 跨页面打磨**：单页产品或直接打磨已有页面时，按相关维度逐项处理。
   - **直接阶段 7**：用户只需要已获批页面、也不需要进一步打磨时，直接完成最终设计系统文档。
   - 可以组合，例如“先 5 后 6”。

**迭代规则**：每次只改用户明确提到的内容。双屏预览中若用户只评论一页，只改该页对应的源码，不暗自重设计另一页。不要主动增加元素；已锁定的内容保持不变。

**产物**：目标平台目录中的 `04-<screen>-v*` 可运行预览源码（或双屏版本）、独立预览入口及 `docs/prototype/design/DESIGN.draft.md`。

**批准门槛**：用户明确表示首屏“可以了”“这样行”或“就用这个”，且 `DESIGN.draft.md` 已生成。

## 阶段 5：核心页面扩展

**目标**：把已批准首屏的方向扩展到验证产品设计系统和关键用户路径所需的最小核心页面集合。这是受约束的扩展，不是新一轮方向探索。

**适用情况**：多页面或多状态产品在阶段 4 后进入此阶段；单页项目可跳过，直接进入阶段 7。

**核心页面集合：**

- 从产品定义和真实用户路径推导，不套固定站点地图。
- 首批优先 3–5 页。数字商品平台可能需要商店首页、商品详情、搜索/分类、结账、购买/下载页；只有创作者流程在范围内时才加入创作者页面。
- 页面应覆盖不同设计压力：品牌表达、信息密度、交易和状态复杂度。
- 核心系统尚未验证前，不要生成所有次要页面。

**关键要求：**

- 以 `DESIGN.draft.md` 为当前事实来源。不得悄悄创造第二套颜色、字体、圆角、按钮或动效系统。
- 使用可信的示例数据和内容。每页包含与职责相关的 default、loading、empty、error 及重要交互状态；只实现验证 UI 所需的本地交互。
- 每页提供 UI 实现契约：平台与预览入口、组件库组件或自定义组件、布局、状态矩阵、交互、示例数据和无障碍要求；不要求真实路由、API 或业务状态管理。
- 生成整组完整预览前，先维护页面地图和组件清单。
- 页面暴露跨产品设计问题时，先更新 `DESIGN.draft.md`，再把决定应用到受影响页面。
- 页面局部例外记录为 `Surface` 规则，不能只藏在预览源码中。

**执行方式：**

1. **确认核心页面集合**：向用户展示拟选页面及其覆盖的用户路径；只有产品范围含糊时才要求修正。生成预览前，先维护 `05-screen-map-v*.md` 和 `component-inventory.md`。
2. **为集合生成 v1**：每页在目标平台目录创建 `05-<screen>-v1` 预览源码，并接入该端的独立预览入口。第一版为中等保真度：结构、内容、组件、状态和响应式意图应可信，但不必做完像素级打磨。沿用阶段 4 的画布规则：手机用竖向手机画框，平板用平板画框，Web/桌面用桌面比例。双端任务分别检查核心任务、示例数据与状态是否一致，允许导航和操作方式适配设备。
   - Web/H5 每页在运行预览中确认阶段 4 的关键工艺问题；再对照 `DESIGN.draft.md` 和组件清单，比较同类组件的字体、圆角、阴影、图片边界、点击区域及交互反馈。重复使用的处理归入现有组件或 token；在页面实现契约中记录发现、修正与暂留项，然后展示页面集合。
3. **收集整组反馈**：展示完整页面集合，问“这个方向放到所有页面后仍合适吗？”
   - 满意 → 进入下方分流决策。
   - 修改 X → 仅为受影响页面生成 v2；若 X 是全局规则，更新所有页面。
   - 将页面 Y 换成 Z 或删去 Y → 调整页面集合，只重新生成受影响页面。
   - 方向不对 → 先询问是调整当前集合，还是返回阶段 4/3；只有用户明确确认方向本身有问题时才返回。
4. **迭代集合**：重复步骤 3，直到用户对整体方向和页面组成满意。全局变更先更新 `DESIGN.draft.md` 并传播；局部变更只更新受影响页面的实现契约，并记录原因。

**探索模式**：用户要求页面或组件的替代方案时启用。替代方案必须保持已选方向和当前设计来源，比较结构差异、适用场景、取舍与实现影响，不做仅换颜色的表面重复。

**产物：**

- 目标平台目录中的 `05-<screen>-v*` 预览源码
- `docs/prototype/design/05-screen-map-v*.md`
- `docs/prototype/design/component-inventory.md`
- `docs/prototype/design/05-<target>-implementation-v*.md`
- 更新后的 `docs/prototype/design/DESIGN.draft.md`

**版本规则**：每轮只为受影响页面、页面地图和已修改的实现契约递增版本；永不覆盖旧文件，保留 v1、v2、v3 供比较。

**批准门槛**：用户批准整个核心页面集合的方向，且每页都有实现契约和当前状态矩阵。

**批准后的分流决策**：向用户主动询问，接下来要进入阶段 6，对字体、间距、组件、响应式或动效做详细打磨；还是当前保真度已足够，直接进入阶段 7 完成 `DESIGN.md`。

## 阶段 6：跨页面打磨

**目标**：把首屏与阶段 5 的核心页面作为一套系统，逐维度打磨。此阶段**可选**；如果用户在阶段 5 后已满意，可以直接进入阶段 7。它用于把一组基本可用的页面变成一致、无障碍且可供开发参考的界面家族。

**三种模式：**

- **单屏模式**：已有页面的窄范围调整，只执行相关打磨项。
- **核心集合模式**：新多页产品，对所有核心页面执行所选打磨项。
- **扩展模式**：阶段 7 后，为新增页面或组件应用现行权威设计来源，再执行相关打磨项并获取批准。

**打磨项顺序**（各项都可跳过；必须与用户确认执行哪些、按什么顺序执行）：

1. **内容与结构**：信息层级、转化路径、导航、内容优先级、标签、CTA 意图、空/错误文案和任务清晰度。按需读取 [clarify](references/clarify.md)。
2. **视觉系统**：字号等级、行高、字距、颜色 tokens、间距节奏、表面、边框、阴影和视觉连续性。按需读取 [typeset](references/typeset.md)、[colorize](references/colorize.md)、[layout](references/layout.md)。
3. **组件与状态**：复用/扩展/新建决策；符合平台的交互状态（Web：hover/active/focus-visible；移动端：tap/press/active）；disabled、loading、empty、error 和领域专属状态。相关时读取 [harden](references/harden.md)。
4. **响应式与无障碍**：代表性宽度、Web 键盘与焦点、移动端触控热区、对比度、减少动效、图片加载、溢出和布局稳定性。相关时读取 [adapt](references/adapt.md) 和 [audit](references/audit.md)；原生平台改读其 native 指引。
5. **动效**：有目的的入场、hover/press、反馈与过渡；缓动和时长 tokens；减少动效回退。相关时读取 [animate](references/animate.md) 和 [audit](references/audit.md)。

**按平台调整顺序：**

- 移动优先产品应更早处理响应式与无障碍，通常紧随视觉系统，或把检查融入每个打磨项。
- 仅桌面产品可稍后处理或简化响应式与无障碍。
- 单页产品通常只需内容与结构、动效；其他项可跳过。
- 每项都可跳过；用户说“跳过 X”或“我们自己处理 X”时，在 `06-polish-log.md` 记录后继续。

**全局打磨与局部打磨：**

- 先修改全局 token 和组件，再检查每个核心页面。
- 全局处理后才引入页面例外，并记录为 `Surface` 规则。
- 不得把某页局部打磨悄悄升级为全局设计决定。

**执行方式：**

1. 第一个打磨项开始前，创建或更新 `docs/prototype/design/06-polish-log.md`。每条记录包含打磨项、允许范围、禁止范围、修改文件、验收标准和用户反馈。Web/H5 先按 [audit](references/audit.md) 在运行预览中完整细查排版、表面、热区、焦点、动效及跨页一致性；记录可见问题、修正计划和暂留项。用户跳过的打磨维度仍记录发现，但不越过允许范围修改。
2. 每次只处理一个维度，不要在无约束的一次请求中同时修改字体、间距、颜色、文案和动效。
3. 每项完成后，在目标平台目录为受影响页面生成新版本 `06-<screen>-v*` 预览源码。不得覆盖原始 `04-*` 或 `05-*` 版本；它们是里程碑。
4. 全局决定要更新 `DESIGN.draft.md`，并重新检查全部核心页面。
5. 某维度需要互动比较（如动效或响应式）时，可选在相应平台的预览入口加入 `06-<dimension>-review` 页面。
6. 进入阶段 7 前进行跨页面复核：确认视觉层级与主要操作清楚，共享组件使用当前 tokens 和状态矩阵，工艺检查中的关键发现已修正或明确记录暂留原因，且没有尚未解决的高严重度漂移。

**产物**：目标平台目录中的 `06-<screen>-v*` 预览源码、`docs/prototype/design/06-polish-log.md`、可选维度评审页，以及更新后的 `docs/prototype/design/DESIGN.draft.md`。

**批准门槛**：用户批准打磨后的核心页面集合；所选打磨项已记录；当前设计来源包含必须带入阶段 7 的全部决定。

## 阶段 7：设计系统（生成 DESIGN.md）

**目标**：把 `DESIGN.draft.md` 固化为最终、可复用的 `DESIGN.md`。

**关键要求：**

- 以 `DESIGN.draft.md` 为输入，**不要**重新从预览源码提取。
- 阶段 5/6 更新过 draft 时，必须合并所有更新。
- 按 `templates/DESIGN-template.md` 的十章骨架组织视觉、组件、布局、UX、工程约束和代理提示。阶段 4 的首屏交互、阶段 5 的 default/loading/empty/error、阶段 6 的打磨都须进入 UX 章节；阶段 5/6 已执行却缺少 UX 规则时，先补齐 draft。工程约束须涵盖跨页一致性、组件选择、技术栈与主题映射、预览方式和验收标准。
- 同时生成 `tokens.css` 和必要资源。

**执行方式：**

1. **读取 `DESIGN.draft.md`**，确认它包含全部获批决策：核心色板、UI 语义 tokens、字体、布局、间距和圆角；阶段 5 已执行则包含多页组件规范与状态，阶段 6 已执行则包含所选打磨项的决定，做过动效项才须包含动效系统。

2. **生成最终 `DESIGN.md`**：以 `templates/DESIGN-template.md` 为骨架，填入 draft 中的实际决定；模板数值和示例不能照抄。章名、表头、字段、解释和示例提示都用用户语言，代码标识符、字体家族名和路径保留原名。按以下清单核对各章：

   1. **设计灵魂**：品牌名称、一句话风格描述、整体气质、色彩策略和字体角色。
   2. **Tokens**：颜色表写名称、`#hex` 值、token 与用途，并说明使用边界；字体写替代字体、字重、字号、行高、字距、OpenType 功能和用途，另列字号等级；间距与形状写基础单位、密度、等级、各元素圆角、阴影、页面最大宽度、章节间距和卡片内边距。
   3. **组件**：至少覆盖按钮、卡片、导航栏、页脚、输入框、标签、价格展示和空状态；逐个写用途、背景、文字、圆角、内边距、字体、平台对应状态及过渡。Web/H5 只映射本次实际使用的组件库或自定义组件及适用端，不要求两端组件逐项对应。
   4. **UX 约束（必需）**：汇总阶段 4–6 已批准的筛选/搜索/排序、导航、表单校验、错误文案、平台对应的交互反馈，以及 default/loading/empty/error。Web 核对对比度、焦点和键盘导航；移动端核对对比度、触控热区和屏幕阅读器标签。缺少此章即未完成。
   5. **该做与不该做**：写出可执行约定、适用的通用禁忌和品牌专属禁忌。
   6. **表面与层次**：按需列层级 0/1/2/3 的颜色和用途，并明确阴影策略，即使决定不用阴影也要记录。
   7. **图像与布局**：记录摄影、插画、logo 墙和禁用内容的风格，以及导航高度、Hero、列宽和纵向节奏。
   8. **响应式行为**：记录断点、移动布局和最小触控热区。
   9. **规范驱动的约束（Web/H5 必需）**：记录实际框架、构建工具、组件库、各端独立预览入口与命令、共用语义 tokens 到各端主题的映射，以及本次使用的组件和验收方式。品牌、信息层级和核心任务一致，控件、布局、导航和操作可适配设备；原型只验证 UI，不把 API 或业务状态管理列为交付要求。
   10. **代理提示指南**：提供颜色速查、可复制的组件提示、常见错误及修法。

   **章节裁剪**：设计灵魂、Tokens、组件、UX、该做与不该做、代理提示为必需。无分层策略时可将第 6 章并入布局；不用图像时可简化第 7 章；仅桌面产品可简化第 8 章；Web/H5 保留第 9 章。渐变、理念和相近品牌按需补充；阶段 6 未做动效打磨时不强加动效章节，做过则详细记录动效与过渡。

3. **生成 `tokens.css`**：提供可直接用于项目的 CSS 自定义属性。
4. **生成资源**：若有 logo、图标等，保存到 `docs/prototype/design/assets/`。
5. **更新 `AGENTS.md`**：在项目根目录加入设计系统引用说明。正常流程引用 `docs/prototype/DESIGN.md` 和 `docs/prototype/design/tokens.css`；已有系统模式引用 `docs/prototype/design/state.md` 记录的当前权威来源，不为满足示例而移动已有来源。例如：

   ```markdown
   ## 设计系统

   本项目的设计系统由 zero-to-design 流程建立。新增页面、组件或视觉改动前，请先阅读：

   - `docs/prototype/DESIGN.md`——完整设计系统文档（tokens、组件库、UX 约束、技术栈与预览方式等）
   - `docs/prototype/design/tokens.css`——可直接使用的 CSS 自定义属性

   所有视觉决策（颜色、字体、圆角、阴影、动效、交互）及 Web/H5 组件选择均以当前权威设计来源为准。
   ```

6. **清理 draft**：`DESIGN.md` 获用户批准后，按用户选择将 `DESIGN.draft.md` 重命名为 `DESIGN.draft.md.bak` 或删除，避免日后混淆。

**正常流程的产物结构（新项目 Web/H5 示例；只创建用户要求的端）：**

```
docs/prototype/design/
├── 01-product.md
├── 02-references.md

│   ├── main.ts

│   └── 06-<screen>-v1.vue
├── h5/                        (H5 任务才创建，同样有独立入口与版本源码)

```

新项目还需在原型工程提供 Vite 的依赖和运行配置；已有项目按其框架选择源码后缀与入口形式，并在状态文件记录实际路径和命令。`04-*`、`05-*`、`06-*` 的旧版本须可复查。

**批准门槛**：用户确认 `DESIGN.md` 完整、准确，并与阶段 5/6 的反馈一致。

## 与现有工具的关系

- **Open Design**：本 skill 可作为其上游流程。先用 zero-to-design 确定方向并完成 `DESIGN.md`，再导入 Open Design 设计后续页面。
- **内部设计能力**：阶段 3–7 按需读取 `references/` 中的规则；`scripts/scan.mjs` 提供有限的 Web 源码机械检查，`scripts/doctor.mjs` 检查状态与产物。
- **定位**：轻量、单代理、可跨会话恢复的设计流程，强调“对话引导 + 磁盘产物 + 持续更新的 `DESIGN.md`”。适合个人开发者或小团队快速从 0 到 1 建立设计系统。

## 失败处理

- 用户拒绝阶段 3 的所有方向：返回阶段 2，重新收集参考，或调整产品定义。
- 阶段 4 多轮仍不满意：最多迭代 5 次，然后建议返回阶段 3 更换方向。
- 阶段 5 暴露核心页面冲突：更新 `DESIGN.draft.md`，在页面地图记录冲突，只重新生成受影响页面。
- 用户不满意阶段 6 的某项打磨：只在受影响页面集合中迭代该维度；若问题属于全局，更新当前权威设计来源并重新应用到所有页面。
- 用户不满意扩展模式的页面或组件：只迭代该目标；涉及跨页面或跨组件规范时，更新当前权威设计来源，并应用到之后的目标。
- 任一阶段文件生成失败：检查对应内部参考文件、目标文件路径与写入权限；Node.js 检查失败时先区分脚本错误、缺少项目文件和真实 finding。

## 完成标准

`DESIGN.md` 已生成且获用户批准时，在 `docs/prototype/design/state.md` 中标记 `status: complete`，并按实际执行的入口与阶段告知用户相应产物（跳过的阶段不列为已完成）：

1. 产品定义（`01-product.md`）
2. 参考收集（`02-references.md`）
3. 方向选择（`03-directions.html`）
4. 首屏预览（目标端的独立预览入口和 `04-<screen>-v*` 源码；确认两页时用双屏预览）
5. 核心页面扩展（目标端的 `05-<screen>-v*` 源码、`05-screen-map-v*.md`、`05-<target>-implementation-v*.md`、`component-inventory.md`）
6. 跨页面打磨（目标端的 `06-<screen>-v*` 源码、`06-polish-log.md` 及可选维度评审页）
7. 扩展模式中生成的页面或组件预览（若执行）
8. 设计系统文档（`docs/prototype/DESIGN.md`、`docs/prototype/design/tokens.css`、`docs/prototype/design/assets/`）
9. 已增加设计系统引用的 `AGENTS.md`，便于今后的代理会话自动读取约束
10. `DESIGN.draft.md.bak`（若用户选择保留原 draft）

正常流程中，生成的 `DESIGN.md` 位于项目根目录下的 `docs/prototype/`，`tokens.css` 和资源留在 `docs/prototype/design/` 下。已有系统模式保留项目原本权威来源的位置，并从 `docs/prototype/design/state.md` 引用。以后开发页面都应遵循当前权威设计来源中的约束；`AGENTS.md` 已指向该来源。
