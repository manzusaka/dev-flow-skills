# Critique：从设计判断和实现证据两面评审

先确定一个稳定目标（方向卡、页面或组件）及其当前设计来源。评审输出是面向用户的报告；阶段 3 的方向判断写入 `docs/prototype/design/state.md` 的候选/拒绝原因，阶段 6 的打磨判断写入 `06-polish-log.md`。不创建 `.impeccable/` 快照。

## 两项评估

**A · 不受扫描结果锚定的设计判断**：先看目标页面及产品定义，评价视觉语言是否服务本产品、主次层级、信息架构、认知负荷、可发现性、字体、颜色、状态、文案、无障碍与边界。按最重要的用户路径考虑首次使用者、熟练用户及目标产品特有用户。记录 2–3 个优点和 3–5 个主要问题。

**B · 源码与浏览器证据**：对本地 Web 文件运行 `node <skill>/scripts/scan.mjs --target <路径>`；有浏览器工具时查看目标画布、响应式状态与主要交互。URL 无本地源码时，只使用可观察的浏览器证据。记录扫描发现、文件位置、误报、浏览器可见问题及无法验证之处。若可用且已获准使用独立代理，两项评估可并行；否则按 A 后 B 的顺序执行。

## 合成报告

不要拼接两份清单。说明两项评估在哪些问题上互相印证，哪里是扫描误报或仅凭渲染无法判断。至少包含：

1. **产品特异性结论**：结构、交互和视觉语言是否来自当前产品，还是可替换成任意品类。
2. **主要路径**：用户从入口到目标操作的理解与负担；同时检查等待、错误、恢复和完成时的情绪变化。
3. **可用性启发式**：可见状态、现实语言、用户控制、一致性、防错、识别优于记忆、效率、简洁、错误恢复与帮助；仅对适用项按 0–4 评分，说明不适用项，不用固定满分掩盖缺项。
4. **优先问题**：每项给 P0–P3 严重度、位置、用户影响、证据与具体修法。
5. **有效做法与待决问题**：保留值得复用的部分；只把需要用户判断的设计选择交给用户。

阶段 3 只评估方向草案能否表达产品和方向间的真实差异；阶段 6 才评估完整页面与状态。使用当前版本的预览和源码，记录所检设备与未检行为；不宣称存在浏览器覆盖层或 Impeccable 检测结果。

## 认知负荷核对

区分任务本身的复杂度、界面额外制造的负担，以及用户学习系统的有效投入。前者需要分步和支架，第二种应消除，第三种可通过一致的反馈支持。逐项检查：单一焦点、可消化的信息组、相关项分组、立即可见的层级、一次一个决策、合理的同时选项、无须跨屏记忆，以及复杂度是否渐进披露。某项不适用时说明原因，不把“四个选项”当作所有产品的硬上限。

常见问题与处理：

| 问题 | 具体修法 |
|---|---|
| 一屏堆放大量等权选项 | 按任务分组、突出推荐或按需展开 |
| 当前步骤依赖用户记住前页数据 | 保留相关上下文或在使用处重现 |
| 导航位置不明 | 显示当前位置、活动态或路径 |
| 术语需要用户自行翻译 | 用受众语言表述，必要术语就近解释 |
| 所有元素同样醒目 | 明确一个主焦点和少量次级重点 |
| 同一操作在不同页面行为不同 | 统一交互模式与文案 |
| 完成一个决定要反复切换页面 | 把做决定所需信息放在一起 |

## 十项可用性启发式

每项 0–4 分：0 表示该项主要路径无法使用；1 表示显著缺陷；2 表示部分成立；3 表示少量缺口；4 表示在目标场景下稳定、清楚。对于说服型落地页等不适用的项目，记 `n/a` 并按实际参与评分的项目计算满分。

| 项目 | 核对重点 |
|---|---|
| 1. 系统状态可见 | 等待、完成、进度、当前位置、表单校验是否及时反馈 |
| 2. 符合现实世界 | 术语、图标、信息顺序是否符合目标用户的经验 |
| 3. 用户控制与自由 | 取消、返回、撤销、清除筛选及退出长流程的路径 |
| 4. 一致性与惯例 | 同一概念、操作和组件是否一致且符合平台 |
| 5. 防错 | 危险动作、输入约束、默认值、草稿恢复是否减少失误 |
| 6. 识别优于回忆 | 操作与选项可发现，帮助就近可见，图标有说明 |
| 7. 灵活与高效 | 熟练用户的快捷路径不增加新手负担 |
| 8. 审美与精简 | 信息、颜色和强调是否都服务当前任务 |
| 9. 错误识别与恢复 | 错误说明具体问题、保留工作并给出恢复动作 |
| 10. 帮助与文档 | 帮助易发现、按任务组织且不迫使用户离开当前情境 |

报告总分时写出实际满分。例如两项不适用，则满分为 32；评级按百分比判断，而不是仍按 40 分的绝对区间。约 90% 以上为优秀，70% 以上为良好，50% 以上为可接受，30% 以上为较差，低于此为严重问题。分数只用于定位薄弱维度，具体问题仍须逐项给证据。

## 角色压力测试

选择与产品有关的 2–3 类用户，沿同一主要路径实际走查：初次接触者是否理解术语和入口；高频用户是否被重复步骤拖慢；依赖键盘、屏幕阅读器或大字的用户是否能完成任务；故意输入边界值的用户是否得到正确恢复；被打断的移动用户是否容易回到任务。以 `01-product.md` 中的典型用户为准补充产品特定角色。报告精确失败点，不输出泛化画像。
