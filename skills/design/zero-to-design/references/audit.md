# Audit：记录可验证的实现问题

Audit 是技术质量检查，不替代 [Critique](critique.md) 的设计判断。Web 使用本文件；iOS/Android 使用 [原生 Audit](native/audit.native.md)。只报告有源码、渲染或实际交互证据的问题，不在审查时顺手修改页面。

## 五个维度（各 0–4 分）

1. **A11y**：实际对比度、语义与标签、键盘/焦点、状态宣告、减少动效。
2. **性能**：资源加载、图片尺寸、布局抖动、昂贵动画、大列表与慢设备。
3. **主题**：语义 tokens 的使用、浅/暗主题、状态颜色和硬编码漂移。
4. **响应式**：窄屏溢出、文字放大、触控热区、断点和真实触控手势。
5. **实现完整性**：组件与权威设计来源的一致性、可信内容、空/错状态和产品特异性。

对 Web 源码运行 `node <skill>/scripts/scan.mjs --target <路径>`，核对每条 finding 的上下文与误报；浏览器检查补足静态扫描看不到的行为。评分含义：0 无法使用，1 严重缺陷，2 部分可用，3 少量问题，4 在该维度表现稳定。总分满分 20，但分数不能替代具体证据。

Web/H5 工艺复核须在运行预览中观察排版断行、数字对齐、表面与图片边界、图标对齐、实际点击热区、焦点和动效中断/离场；多页面时比较同类组件与语义 tokens 的一致性。将可见问题、修正结果和暂留项写入当前阶段的反馈或打磨记录。源码扫描只提供线索，不代表这些项目已经通过。

## 审计主张

- 沿主要任务检查操作后是否及时显示可信结果；把使用户误判状态的问题列为发现。
- 比较页面名称、导航入口和同一操作的表达，指出破坏熟悉感的具体不一致。
- 分别检查权限对入口可见性、操作可用性和受限反馈的影响，并记录实际证据。

## 报告

先给出实现完整性判断，再给五维评分、2–3 个有效做法及按 P0–P3 排序的问题。每项问题记录位置、用户影响、证据、修复建议与对应本地能力（如 `layout`、`typeset`、`adapt`、`harden`）。P0 阻断任务；P1 显著影响任务或违反关键无障碍要求；P2 有替代路径但造成困扰；P3 低影响打磨。将本轮选择的处理项写入 `06-polish-log.md`；未选择的维度按阶段 6 规则记录跳过。

完成标准：每个 finding 经人工核对，误报被标明，不能把静态扫描结果称作运行时验证。
