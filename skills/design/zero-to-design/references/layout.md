# Layout：用结构表达产品优先级

先诊断阅读顺序、分组、节奏、密度和适配，再移动元素。方向已锁定时，调整结构应沿用当前视觉身份；新的布局方向须经过阶段 3 或阶段 5 的对应用户决策。

## 两次检查

1. **结构检查**：在代表性画布与状态下回答：第一眼焦点是什么？哪些内容属于一组？紧凑与宽松的间隔是否有节奏？区域拓扑是否匹配任务？信息密度是否适合使用频率？窄屏、长文案、空状态和弹层下如何重排？视觉顺序是否与 DOM、焦点或朗读顺序一致？
2. **机械检查**：对 Web 源码运行 `node <skill>/scripts/scan.mjs --scope layout --target <路径>`。扫描只能提示可疑写法，不能证明视觉层级正确。原生界面另读 [iOS](native/ios.md) 或 [Android](native/android.md)。

## 结构主张

- 用内容关联决定距离与分组，关联越强越接近，并为同类内容建立统一视觉起点。
- 为全局导航、当前位置和内容区域确定稳定职责；页面变化时让用户仍能辨认自己在哪里。
- 通过有目的的对比显示主次，不让所有区域同等醒目。

在编辑前说明主要任务路径、主次元素、相关分组、目标密度和不同设备下的重排方式。优先用内容关系决定网格、列表、容器与 `gap`；重复仅在内容真正等价时使用。组件在不同容器中出现时，考虑容器宽度和内容极端值。阴影只用于解释层级或状态。

Web/H5 的运行预览还要核对：嵌套表面的内外圆角是否随内边距形成一致关系；同一层级的阴影是否表达相同高度；图片边界、裁切与相邻表面是否协调；图标与文字、按钮是否在视觉上对齐。这些都以当前 `DESIGN.md` 和实际组件为准，不套用固定数值。

## 应用与验证

- 先更新共享布局 token 或组件，再处理明确的页面例外。不得把局部变化悄悄升为全局规则。
- 检查窄、中、宽视口及必要的缩放、本地化、长内容、empty/loading/error 状态。
- 确认键盘、触控和辅助技术的顺序与可见布局一致；给出渲染或源码证据，并重新运行受影响范围的扫描。
- 更新页面地图、实现契约和 `DESIGN.draft.md` 中确实改变的规则，再生成受影响页面的新版本。
