# Interaction state：确认页面操作与状态

在阶段 4、5、6 迭代设计页时，若关键操作会改变业务状态、操作可用性或页面反馈，先确认其行为再更新预览。纯展示页面和仅涉及 hover、排版的改动无需使用本能力。

## 确认方式

1. 从当前页面的核心任务中找出相关操作。已有系统先核对相关页面、操作处理、领域模型或测试，区分已实现行为与拟议改动；新产品从已确认的产品定义和设计决策出发。
2. 对每个影响设计的操作，明确谁能触发、前置条件、原状态 → 目标状态，以及等待、成功、失败和恢复时页面显示什么、允许做什么。将代码已证实的事实、推断和待决定规则分开。
3. 只把会改变页面或交互的未决规则交给用户确认，并说明不同答案对页面的影响。用户反馈只影响部分操作时，沿用其余已确认规则。
4. 用本地状态在预览中表现已确认的规则；不把预览当作真实 API、权限或业务状态管理的验证结果。

## 记录与完成条件

- 阶段 4：首屏获批后，将相关操作与状态反馈写入 `DESIGN.draft.md` 的 UX 约束。
- 阶段 5：将每页规则写入现有状态矩阵和页面实现契约；跨页面共用的规则同步到 `DESIGN.draft.md`。
- 阶段 6：仅在本轮打磨涉及操作或状态时，将决定写入 `06-polish-log.md`；全局规则变化更新当前权威设计来源。

完成时，受影响页面的预览与记录使用同一套已确认规则；仍未决定的规则明确标记，不伪装成已验证行为。
